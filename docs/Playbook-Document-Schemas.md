# AI-First Playbook — Document Schemas

| | |
|---|---|
| Purpose | For each document the Playbook produces: the sections it must have, in order; how big it may be; and what every row must contain. Checker scripts enforce this, so a document cannot drift from its shape. |
| Audience | Maintainers and approvers. Agents read the same rules in machine form (`playbook/*-schema*.json`). |
| Status | Generated by `scripts/document-schemas-doc.mjs` from the schema files; do not edit by hand. Built in reset Sessions 4 and 6 (2026-09-26). |
| Checkers | `checklist-lint.mjs`, `handoff-record.mjs validate`, `doc-check.mjs`, `template-lint.mjs` |

## 1. How a schema works

Each schema names the required sections in order, the optional ones, a word budget per size as TARGET / MAXIMUM, and the rule every row follows. The TARGET guides normal writing; the MAXIMUM fails the check. A scaffold script writes the skeleton; the checker prints one line per problem and exits non-zero.

## 3. Implementation checklist

Required sections in order: Status Table; Infrastructure Requirements; Deployment Steps; Verifier Run Log. Optional: Verified History; YOLO Decisions.

Item fields in order: Type; Behavior; Location; UI ref; Logging; Acceptance; Verify; Coding Standards; Depends on. Required: Type, Behavior, Location, Logging, Acceptance, Verify, Coding Standards; UI ref also for ui and desktop items. Types: ui, backend-api, backend-service, db, logging, infrastructure, cross-cutting, desktop.

Item budget: 90 / 130 words at every size. Acceptance: "When <actor> <does what> on <screen>, then <observable result>", target 20, maximum 30 words, one behaviour, no subjective words. Verify names an assertion and retained evidence. Metadata keys in order: schema, id, owner, priority, risk, status, created_at, updated_at, evidence, misses. Checker: `checklist-lint.mjs`.

## 5. Human documents

Scaffold: `doc-scaffold.mjs <kind> <out> --feature=<name>`. Checker: `doc-check.mjs <doc> --size=<size>`.

### 5.1 Developer Flow Guide — `docs/<feature>/<Prefix>-<Feature>-Developer-Flow-Guide.md`

Metadata rows: Purpose; Scope; Subject type; Audience; Companion docs; Updated by; Last synced to code.

Sections in order: Map; Screen / Tab flows (when Subject type is UI or Mixed); Service / package / job flows (when Subject type is Service/Job, Package or Mixed); Cross-cutting flows; Where do I look.

| Size | TARGET / MAXIMUM words |
|---|---:|
| small | 900 / 1,500 |
| medium | 1,800 / 3,000 |
| large | 3,000 / 5,000 |

Every row: Every flow row or step names a real identifier in backticks, or is marked [VERIFY], [PLANNED] or [KNOWN ISSUE]; diagrams are Mermaid flowcharts; no code listings.

### 5.2 Business Verification Reference — `docs/<feature>/<Prefix>-<Feature>-Business-Verification-Reference.md`

Metadata rows: Purpose; Audience; Plain English; Last reviewed.

Sections in order: What this report shows; Data sources; Calculation logic; Mapping tables; How to verify a value; Verification scenarios; Glossary.

| Size | TARGET / MAXIMUM words |
|---|---:|
| small | 700 / 1,200 |
| medium | 1,400 / 2,400 |
| large | 2,400 / 4,000 |

Every row: Plain English only: no SQL, code, file paths or internal names; every data source names its portal path; a mapping table whenever sources are normalised.

### 5.3 DB Changes — `docs/<feature>/<Prefix>-<Feature>-DB-Changes.md`

Sections in order: Tables; Stored procedures and views; ER diagram; Field-to-mockup mapping.

| Size | TARGET / MAXIMUM words |
|---|---:|
| small | 600 / 1,200 |
| medium | 1,200 / 2,400 |
| large | 2,400 / 4,000 |

Every row: Full DDL per object; one mapping row per UI field; the ER diagram is a Mermaid erDiagram.

### 5.4 Architecture — `docs/<feature>/<Prefix>-<Feature>-Architecture.md`

Sections in order: System diagram; Service design; Data flow; Error handling and logging; Integration points.

| Size | TARGET / MAXIMUM words |
|---|---:|
| small | 500 / 1,000 |
| medium | 1,000 / 2,000 |
| large | 2,000 / 3,500 |

Every row: One service or integration per row with its registration site; the system diagram is a Mermaid flowchart.

### 5.5 Verification Guide — `docs/<feature>/<Prefix>-<Feature>-Verification-Guide.md`

Sections in order: Prerequisites; Base URL; Test data profile; Testing steps; Data verification; Local setup.

| Size | TARGET / MAXIMUM words |
|---|---:|
| small | 500 / 1,000 |
| medium | 1,000 / 2,000 |
| large | 2,000 / 3,500 |

Every row: One numbered step per action; connection profiles by name, never a connection string or secret.

### 5.6 Power BI Mapping — `docs/<feature>/<Prefix>-<Feature>-PowerBI-Mapping.md`

Sections in order: View to dataset mapping; Business logic; Filters and parameters.

| Size | TARGET / MAXIMUM words |
|---|---:|
| small | 300 / 700 |
| medium | 700 / 1,400 |
| large | 1,400 / 2,500 |

Every row: One view or measure per row; business logic in plain English, no DAX.

## 6. Documents never rendered to HTML

`*-Implementation-Checklist.md`, `*-Checklist.md`, `*-Issues.md`, `*Issues.md`, `*AGENTS.md`, `*-Requirements.md`, and any checklist. `render-docs.mjs` skips them.
